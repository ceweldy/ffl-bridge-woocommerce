# Jenkins shadow migration

GitHub Actions remains authoritative. `Jenkinsfile` is a manual, credential-free shadow path: it accepts one exact `SOURCE_SHA`, checks out that commit, runs the workflow's checks, transfers immutable assets, and archives JSON receipts. It cannot create GitHub releases or commit to SVN. No Actions workflow, Dependabot configuration, webhook, credential, permission, runner, or protection setting is changed by this migration.

## Contract and safe operation

The requested result is reviewable Jenkins implementation with observable parity evidence before cutover. Acceptance is an exact checkout receipt, all matching quality lanes, real ZIP/checksum validation, a checked artifact transfer, correct publication destination plan, and explicit failed/blocked evidence. Plugin runtime behavior and existing Actions authority remain unchanged. Changed modules are `Jenkinsfile`, `ci/jenkins/*`, and release exclusions in `.distignore`. Live Jenkins/security setup and actual publishing are outside this shadow change. Rollback is to stop the shadow job; Actions continues as before.

Load the Jenkinsfile and scripts through Pipeline from SCM pinned to a reviewed tooling commit. Never load pipeline Groovy or these scripts from an untrusted PR revision. Source under test is a separate checkout; receipts contain both source and tooling SHA. Jenkins needs Pipeline and Git. Set controller-owned `SHADOW_TOOLING_SHA` to the approved full 40-character tooling commit; every stage rejects an SCM tooling checkout that differs before executing its scripts. Validate the file with the target controller's Pipeline linter before creating/enabling a job. The controller linter and live execution have not been run during preparation.

Before the first run, create one job per exact `(repository, workflow, ref)` concurrency group and bind controller-owned `SHADOW_WORKFLOW`, `SHADOW_EVENT`, `SHADOW_REF`, and approved `SHADOW_TOOLING_SHA`. Preconfigure the matching concurrency option as well as the runtime property; runtime `properties` cannot establish first-run queue behavior. Do not give submitters permission to change these bindings or configure jobs. Each job takes only `SOURCE_SHA`. Do not multiplex refs or workflow/event types in one job: `disableConcurrentBuilds` is job-scoped. Multiple branch jobs can execute independently.

| Workflow | Accepted event/ref | Quality | Dependency/failure behavior | Concurrency | Time limits |
| --- | --- | --- | --- | --- | --- |
| `ci` | push `refs/heads/main`, PR `refs/pull/N/merge` | PHP 8.3, 8.4, 8.5 | No fail-fast; package waits for all quality lanes | Cancel previous run in that group | 10 min/lane, then 5 min package |
| `release` | push `refs/tags/v*` | PHP 8.3 | Package waits for quality; plan waits for transfer verification | Queue; never abort prior tag run | 10 min quality+build, then 5 min consumer |
| `wporg` (public only) | PR merge ref or `v*` tag push | PHP 8.3 + Plugin Check | Directory check must succeed before publication plan | PR cancels previous; tags queue | 15 min combined dry run, then 15 min plan |

Actions PR checkout uses the merge SHA, not the contributor's head SHA. Obtain the exact event SHA from the Actions run being compared. Main ref resolves to `refs/remotes/origin/main`; PR merge refs and tags are fetched explicitly. Changed/moved refs fail closed, so capture/refetch the intended ref and record the mismatch instead of substituting a newer SHA. Tags are peeled to commits and must match the plugin header; the canonical build script checks version invariants. Public directory builds also check `Stable tag`. A shadow tag replay does not create a tag or release.

Agent labels are generic capabilities, not machine identities: `ffl-php83`, `ffl-php84`, `ffl-php85`, `ffl-package`, and public-only `ffl-wporg`. PHP agents need that exact minor runtime, Composer v2, Node, bash, and existing Composer extensions. Package agents need git, bash, python3, rsync and ZIP support. WordPress.org needs Node 24, npm, and exclusive single-executor disposable Docker workers under `ffl-wporg`; each worker must own its Docker daemon and fixed ports, with no other jobs or agents sharing them. The node scheduler serializes checks on each worker, so no lock plugin is required. Provisioning or changing those workers requires action-time approval. Do not assign credentials or controller/network administration capability to test agents. Jenkins private SCM checkout may reference a controller-owned read-only `SHADOW_SCM_CREDENTIALS` ID; it is never bound to the shell. Any grant, credential creation, agent change, webhook, or live job change requires separate action-time approval. Do not configure any of those during code preparation.

## Exact receipts and artifacts

`shadow.py` can run locally with no Jenkins:

```sh
python3 /path/to/reviewed/ci/jenkins/shadow.py \
  --source /path/to/fresh/exact/checkout --sha FULL_40_CHARACTER_SHA \
  --workflow ci --event push --ref refs/heads/main \
  --stage package --output /path/to/receipts
```

Stages are `context`, `quality` (select `--php`), `package`, `verify`, `plugin-check` (public only), and `plan`. `package` requires a fresh checkout with no `dist`; `verify` checks an existing artifact set; `plan` additionally checks the transferred successful `package.json`. Jenkins uses a fresh isolated workspace per stage. The producer stashes ZIPs, checksum files, and package receipt as `release-assets`; consumers unstash that exact build's bytes and recheck the exact names, sizes, checksums, exclusions and CRC. Plugin Check unpacks the validated directory ZIP. Release assets cannot be reconstructed in the consumer or silently replaced with a newer build.

Every runner invocation records a stage JSON receipt, including command/runtime failures. HEAD, tracked-source cleanliness, and exact event-ref resolution are checked again after every stage before success. Fields include repository, exact source SHA, tooling SHA, event/ref, lane, result, timestamp, and each artifact name/size/SHA256. Jenkins also writes a receipt for checkout failures/abort and fingerprints archived bytes. Its nested finalizer removes the workspace even if receipt or artifact archival fails. Agent loss can prevent receipt archival; Jenkins' failed/aborted build result is then required evidence and must never be considered parity success. A timeout must fail the whole dependency path. Preserve the failing logs and receipts; do not proceed to package or plan after failure.

Release archives/checksums use one-day retention, matching `upload-artifact` release settings; Jenkins logs retain 90 days. Jenkins archives are not a substitute for GitHub's immutable artifact IDs, attestation/access controls or default Plugin Check report retention. Per-artifact report retention and an exact GitHub artifact comparison are cutover blockers until demonstrated. Download matched Actions artifacts before they expire and compare all bytes/checksums with the same SHA. Public CI builds self-hosted ZIP after running `tests/build-release-test.sh`; public release builds self-hosted plus wporg; private prelaunch builds only its self-hosted ZIP. Jenkins source/CI files are explicitly excluded from distributable ZIPs.

## WordPress and release destination parity

The release plan targets this repository's GitHub release, same `v*` tag, generated notes and title `FFL Bridge for WooCommerce X.Y.Z`; it lists exactly the canonical ZIP/checksum artifacts. Existing Actions runs `gh release create ... --generate-notes --verify-tag`. Shadow replay never invokes it.

Public WordPress.org uses `ffl-bridge-for-woocommerce`, directory ZIP, no self-hosted updater file or `Update URI`, and the four required banner/icon assets. The implementation reproduces the pinned `WordPress/plugin-check-action` 1.1.9 core path: Node 24; latest `@wordpress/env` and WordPress; up to 3 start attempts (10 minutes each under the overall job limit); install/activate Plugin Check, install declared plugin dependencies, activate the plugin; experimental checks; JSON output; fail on `ERROR`, warnings advisory. Runtime versions and the raw results are receipts. Its GitHub PR comment/annotation integration requires a separate read-only/status publishing design and has not been migrated; shadow posts no comments.

The existing deploy is gated by `wordpress-org` environment approval and secrets `SVN_USERNAME` and `SVN_PASSWORD`. Missing either produces a notice and skips deployment. Tag, header, and `Stable tag` must agree. The pinned 10up deploy action 2.3.0 preserves `https://plugins.svn.wordpress.org/ffl-bridge-for-woocommerce/`, copies the validated build to `trunk/` with deletions, syncs `.wordpress-org/` to `assets/`, creates `tags/X.Y.Z` in one SVN commit, sets image MIME types, and skips a version already published. A future publisher must preserve those semantics, environment gate, no-auth-cache handling, and skip behavior. This change produces that destination plan only; SVN checkout, credentials and commits have not been executed.

The self-hosted updater URL and fflbridge.com manifest remain the separate existing human publication path. Private prelaunch has no WordPress.org workflow or publication destination. Never send its source or artifacts to the public repository or directory.

## Dependency Actions and cutover gates

Both repositories keep weekly Monday 09:00 America/New_York Dependabot Composer development-dependency group and grouped pinned GitHub Actions updates, limit 5 open PRs each. Dependabot PRs retain the same CI semantics and must run without secrets. Pinned Actions are evidence of implementation versions, not Jenkins plugins: checkout v7 maps to GitSCM; setup-php 2.37.2 maps to explicit runtime lanes and Composer v2; upload-artifact v7/download-artifact v8 map to verified stash plus fingerprints; Plugin Check 1.1.9 and 10up deploy 2.3.0 are detailed above. Mutable tool dependencies (`ubuntu-latest`, Composer 2 latest, npm wp-env, WordPress, Plugin Check) require recorded runtime snapshots and same-SHA comparison. Jenkins/runtime dependency update ownership is still to be assigned; no replacement updater is enabled.

Before any cutover, attach passing Actions and Jenkins receipts for at least a main commit, same-repo PR merge SHA, dependency PR and rejected/failing source; demonstrate independent ref concurrency, canceled PRs and queued tag runs; verify all PHP lanes and deterministic artifact bytes; execute Plugin Check on a disposable agent; validate GitHub status/check naming and trust boundaries; confirm required checks, tag protections and environment reviewer gates. Public tag replay must use a commit whose version matches an existing tag. Do not retag/release merely to obtain migration proof.

Tag protections must continue to reject unintended `v*` creation, update and deletion; inventory is evidence, not a protection configuration change. No required check switches to Jenkins until live parity passes and the owner approves the action. Keep Actions enabled for rollback until Jenkins is proven. Actual GitHub release and SVN mutation remain blockers and require approval at execution time; credential/security changes cannot be preapproved by this document.
